# 관리자 검토가 필요한 릴리스 정책

v0.12에서 신규 정책은 선택적으로 관리자 검토를 요구할 수 있다. 기존 정책과 자동 승인 흐름의 기본값은 유지한다. 화면의 정책 등록에서 ‘관리자 검토 필요’를 선택하거나 아래 정책 계약을 사용한다.

```json
{"name":"Administrator reviewed release","minimumPassRate":1,"requiresManualApproval":true,"manualApprovalTtlSeconds":3600}
```

승인 유효 시간은 60~86,400초이며 생략 시 3,600초다. TTL은 검토 요구 정책에서만 허용한다. 정책은 불변 버전이므로 기존 실행에 소급 적용하지 않는다.

이 정책의 평가가 통과하면 평가 gate.decision은 pass이고 evaluationPassed는 true지만 deploymentAllowed는 false다. 화면도 ‘관리자 승인 필요’로 표시한다. DB 트리거가 승인 요구 실행의 자동 배포 허용을 거부한다. 실패한 필수 규칙·실행 오류·불완전한 증거는 관리자 승인이 있어도 통과하지 않는다.

일반 관리자 세션만 `POST /v1/runs/:id/reviews`로 approved 또는 rejected와 최대 500자 comment를 저장한다. 유효한 Idempotency-Key를 요구하며 동일 요청 재시도는 기록·감사를 한 번만 만든다. 키의 충돌은 409다. CI 서비스 키, 작성자, 조회자는 검토를 작성하지 못한다. 조직·프로젝트 밖 실행은 404다. 일반 세션은 자기 프로젝트의 검토 이력을 조회할 수 있다. 무쿼리 요청은 최근 50개 배열을 유지하며, limit/cursor 요청은 기본 25개·최대 100개씩 저장 순서 기준으로 조회한다. 커서는 조직·프로젝트·실행에 묶이며 UI에서 이전 검토를 계속 읽을 수 있다. 승인 생성 시 저장된 근거와 규칙·버전·요약·게이트의 일치를 검증한다.

검토 기록은 평가의 실행 ID·조직·프로젝트·스냅샷·결과 해시, 검토자, 의견과 시각을 포함하고 append-only로 보존한다. 관리자 역할은 평가가 완료되고 통과한 경우에만 승인할 수 있다. 완료된 실패 실행은 반려할 수 있지만 승인할 수 없다. 의견은 화면에서 텍스트로만 표시하고 감사 이벤트에는 원문을 넣지 않는다.

CI 게이트는 현재의 마지막 검토를 DB 순서 번호로 찾는다. 시각이 뒤로 움직여도 나중에 기록한 반려가 먼저 기록한 승인보다 우선한다. 승인 요구 실행과 다른 증거, 만료·미래 시각, 비활성/관리자 권한을 잃은 검토자, 검토 없음, 반려는 모두 차단한다. 새로운 승인은 별도 기록으로 추가한다. 과거 승인 요청의 중복 재전송으로 최신 반려를 덮어쓸 수 없다.

CI 기록에는 현재 검토 상태·ID·내용 해시가 들어가며 Ed25519 서명에도 포함된다. 현재 평가 버전·결과 유효 시간·완전성·선택한 기준 실행 비교도 함께 확인한다. 이미 통과한 CI 요청을 재전송할 때 검토 상태가 달라졌다면 409다. 배포 직전에는 새로운 체크 키로 다시 검증한다. 승인·CI 검증의 잠금 순서를 맞춰 동시에 발생한 반려와 검증을 순서대로 처리한다.

검토 시 DB 시간을 사용하며 CI 자격증명은 잠금 대기가 끝난 뒤에도 만료·철회를 재확인한다. 검토 기록은 조직당 분당 120개, 총 100,000개로 제한한다.

실제 배포를 실행하지 않는다. 현재 관리자는 본인이 만든 실행을 검토할 수 있고, 2인 승인·역할 분리·OIDC 사용자 인증·운영 승인 조직 정책은 아직 구현하지 않았다. 관리자 역할로 승인했다는 기록이 실제 사람의 개입을 별도로 증명하는 것은 아니다.

`node scripts/manual-review-smoke.mjs`는 합성 mock 실행으로 차단→승인→서명 검증→반려를 점검한다. 마지막 예제는 차단 상태로 유지하며 private 결과는 `.local/manual-review-smoke.json`에 저장한다. LogiTrack이나 외부 시스템에는 연결하지 않는다.

## 검토 요청 중 워크스페이스 전환 — v0.66

프로젝트 전환·로그아웃 시 현재 화면의 검토 대기 상태를 초기화한다. 이전 워크스페이스에서 시작한 요청의 종료 처리는 새 워크스페이스의 대기 상태나 최종 게이트를 변경하지 않는다. 이전 서버 요청은 이미 처리됐을 수 있으므로 취소 또는 기록 삭제로 해석하지 않는다. 현재 워크스페이스의 기록을 새로 조회해 결과를 확인한다.

## 검토 중 실행 재선택 — v0.67

검토 요청은 실행 ID·워크스페이스·실행 선택 시점에 묶인다. 같은 실행을 다시 조회한 뒤 작성한 새 의견은 이전 요청의 늦은 성공 응답이 지우지 않는다. 검토·감사 조회 중 실행을 바꾸면 이전 성공/오류 안내도 새 선택의 상태를 덮어쓰지 않는다. 이미 보낸 검토의 서버 처리 여부는 현재 기록을 조회해 확인하며 요청 종료 후 최종 게이트를 다시 확인한다.


## 연결된 과거 관리자 검토 근거 — v0.121

검증 기록 상세는 기록에 포함된 검토 ID·해시에 해당하는 원래 관리자 의견을 조회한다. 조직/프로젝트·후보 실행·스냅샷/결과 해시·검토 판정·시각과 실제 본문 해시를 결합한 뒤 텍스트로 표시한다. 나중에 반려가 추가되거나 검토자의 권한이 바뀌어도 과거 의견 조회는 현재 승인을 복원하지 않는다. 연결된 검토가 없거나 모순이면 확인된 검증 기록은 유지하며 별도 실패 안내를 표시한다. 서명 검증은 독립 공개키 CLI의 책임으로 유지한다.

서버는 검토 해시와 함께 저장 행의 ID·조직·프로젝트·실행·검토자·판정·시각을 대조한다. 올바른 해시를 가진 모순된 본문도 목록·상세·최종 게이트에서 503으로 차단하고 의견 원문을 오류에 포함하지 않는다. 이를 변경 전 실패로 재현했다. `demo:evidence`의 viewer 단계도 원래 승인·반려 의견 두 개를 조회해 서명 artifact에 포함된 ID·해시와 대조한다.

상세 닫기는 원래 버튼 또는 기록 패널로 키보드 포커스를 돌려준다. 검색 결과가 없는 경우는 전체 기록이 없는 경우와 안내를 구분한다. 로그아웃·닫기·조회 조건 초기화 뒤의 늦은 의견 응답이나 해시 계산이 이전 상세를 복원하지 않는다.
