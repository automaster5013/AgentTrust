# 새 스택의 JSON 입력과 응답 경계

Next.js BFF는 요청을 최대 16 KiB, 중계 응답을 최대 1 MiB의 UTF-8 바이트로 제한한다. 전체 본문을 먼저 읽은 뒤 크기를 검사하지 않으며, 스트림을 읽는 도중 한도를 넘으면 취소한다. 요청 본문 읽기·Java/WebFlux 중계·응답 읽기는 하나의 10초 기한을 공유한다. 사용자가 요청을 중단해도 같은 신호로 중계를 취소한다.

크기를 초과한 요청은 413, 잘못된 요청 UTF-8은 400 `INVALID_JSON_TEXT`다. 응답 한도·UTF-8·네트워크·기한 실패는 기존 502 `REQUEST_UNAVAILABLE`로 처리하며 응답 원문을 오류에 포함하지 않는다. 로그인 폼의 미디어 타입과 세션·CSRF 전달 범위는 기존 계약을 유지한다.

Java Core API도 POST 실행·버전·캠페인·내부 완료/예약의 JSON 본문을 파싱 전에 16 KiB로 제한한다. 엄격한 UTF-8로 읽은 뒤 JSON 문자열과 필드 이름의 NUL·짝이 없는 UTF-16 surrogate를 400으로 거부한다. PostgreSQL 저장 실패 또는 해시 생성 시 문자 대체로 넘어가지 않도록 하는 경계다. 한글·다국어·정상 이모지는 원래 바이트를 유지한다. UTF-16 인코딩 본문을 UTF-8 JSON으로 자동 추정하지 않으며, Java에 UTF-8이 아닌 charset을 명시해 검증한 문자를 재해석하는 요청도 거부한다.

소스 검증은 Java 82개와 TypeScript 67개 테스트·타입 검사에서 통과했다. 스트림 검사 9개에는 실제 loopback HTTP의 큰 응답 취소와 헤더 후 멈춘 응답의 시간 제한·연결 종료도 포함된다. 실행 서비스 반영과 실제 OIDC/BFF의 잘못된 입력 검사 완료는 별도 검증 근거로 기록한다.

```powershell
python scripts/stack-json-text-smoke.py --stalled-body
```

이 명령은 자기 OIDC 세션으로 잘못된 문자/인코딩 요청 여섯 개의 실제 거부 경로를 확인하고, 종료되지 않은 chunked 요청 본문이 시간 제한으로 중단되는지도 검사한다. 새 버전·평가·승인·모델 호출을 생성하지 않으며, 전후 15개 업무 테이블의 지문을 대조하고 자기 세션을 종료한다. 로컬의 한도와 검증은 운영 ingress·TLS·고객 부하 SLO의 완료를 뜻하지 않는다.
