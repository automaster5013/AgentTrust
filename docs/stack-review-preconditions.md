# 화면에서 확인한 검토 순서와 조건부 저장

평가와 캠페인의 관리자가 최신 검토를 읽은 뒤 다른 검토자가 승인·반려를 추가할 수 있다. 새 Console은 저장 전에 확인한 최신 검토 순서와 결정·사유·검토자를 표시하며, 그 순서에 조건을 걸어 저장한다. 기준 조회가 실패하거나 다른 조직·프로젝트·평가의 응답이 오면 저장할 수 없다.

기존 `POST /api/runs/{id}/reviews`와 `POST /api/campaigns/{id}/reviews`에 선택적인 `expectedReviewSequence`를 추가했다.

```json
{"decision":"approved","reason":"검토한 근거와 변경 내용을 확인함","expectedReviewSequence":17}
```

값은 JSON 정수이며 0부터 9,007,199,254,740,991까지 허용한다. 문자열·소수·불리언·명시한 null·배열·객체는 거부한다. 0은 검토 기록이 없음을 확인한 경우다. 순서는 전역 시퀀스에서 배정하므로 같은 평가에서 연속된 수일 필요가 없다.

서버는 해당 조직·프로젝트와 대상의 접근 권한을 확인하고 기존 검토 트랜잭션 잠금을 획득한 뒤 최신 순서를 대조한다. 순서가 달라졌으면 HTTP 409로 거부하며 검토와 감사 기록을 추가하지 않는다. 같은 기준의 두 조건부 요청이 경쟁하면 먼저 저장된 요청 이후의 요청은 거부한다. 새로 조회한 순서를 사용한 명시적 재제출도 기존 평가 통과·버전 수명·관리자 권한 조건을 우회할 수 없다.

필드를 생략한 기존 API 호출은 원래의 조건 없는 추가 동작을 유지한다. 따라서 모든 외부 클라이언트가 동시 변경을 보호한다고 주장하지 않는다. 동시 검토를 보호하려는 클라이언트는 최신 `reviews/page` 응답의 첫 기록 순서 또는 빈 기록의 0을 확인하고 필드를 반드시 제공해야 한다. 서명되지 않은 검토 이력은 현재 배포 권한을 부여하지 않는다.

Console은 충돌 시 현재 게이트를 지우고 새 기준을 조회해 표시한다. 자동으로 검토를 다시 제출하지 않는다. 저장 응답의 ID·결정을 검증한 경우와 그 뒤 현재 게이트 조회가 실패한 경우를 구분한다. 선택이나 인증 범위가 바뀌면 이전 기준을 사용할 수 없다. 조회는 10초·1MiB 제한을 적용한다.

## 검증 범위

Java의 정확한 정수·빈 기록·순서 불일치 검사와 평가·캠페인 양쪽의 충돌 시 쓰기·감사 미실행을 검사한다. 브라우저는 기존 데이터 읽기와 가로챈 POST 응답으로 충돌·기준 갱신·명시적 재제출·잘못된 범위·저장 응답 이후의 게이트 실패를 검사한다. 로컬 브라우저 실행은 `STACK_E2E_READ_ONLY=true`로 업무 변경의 네트워크 전달을 차단한다.

`scripts/stack-review-precondition-smoke.py`의 기본 경로는 조회자의 조건부 검토 거부만 확인한다. 실제 경쟁·저장은 `--allow-synthetic-writes`를 지정한 고정 GitHub Actions 격리 경로에서만 허용한다. 이 경로는 별도 합성 평가와 두 독립 세션을 사용해 소스·레지스트리 환경 각각에서 경쟁 요청 하나만 저장됨, 오래된 승인 거부, 새 기준의 명시적 반려와 현재 게이트 차단을 확인한다. 로컬 업무 데이터에 경쟁 검토를 생성하지 않는다.

CI 업로드 목록에 평가 검토 이력·소유 요청 조회·조건부 검토 진단 JSON을 포함한다. 이전 `6c1e91c`의 누락 파일은 인증된 정확한 작업 로그로 별도 검증했으며, 새 업로드 목록의 실제 전달 결과는 새 revision의 CI가 완료된 후에만 확인한다. 운영 인증·신뢰키·실제 배포 준비와 Grafana 전체 이미지 보안 문제는 별도 미완료 범위다.
