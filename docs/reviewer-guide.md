# AgentTrust를 처음 살펴보는 순서

기업 개발팀의 에이전트 변경을 고정된 평가 기준으로 검사하고, 근거·회귀·관리자 검토를 바탕으로 릴리스 여부를 판단하는 로컬 포트폴리오다. 합성 사례와 모의 에이전트를 사용한다. 실제 고객 모델 연결·SSO/OIDC·상용 서버 배포는 다음 제품 단계다.

## 1. Docker 없이 핵심 판정을 확인한다

Node.js 24가 설치된 저장소 루트에서 실행한다. 아래 명령은 공개 예제만 읽으며 접근 키·Docker·외부 연결이 필요 없다.

```powershell
npm.cmd ci --cache .cache/npm --ignore-scripts
npm.cmd run demo:offline
```

의존성 설치에는 npm 레지스트리 연결이 필요하다. 설치 후 `demo:offline` 자체는 네트워크를 사용하지 않는다. 자동화에서 JSON만 필요하면 `node scripts/portfolio-offline.mjs --json`을 실행한다. 다른 셸에서는 `npm.cmd` 대신 `npm`을 사용한다.

| 합성 사례 | 평가 판정 | 의미 |
| --- | --- | --- |
| 정상 응답 | pass | 고정 규칙을 충족 |
| 업무 회귀 | block | 필수 규칙 실패 |
| 금지 도구 호출 | block | 허용 목록 밖의 도구 사용 |
| 근거 누락 | inconclusive | 누락을 정상 응답으로 대체하지 않음 |
| 실행 오류 | inconclusive | 실행 실패를 통과로 처리하지 않음 |

`succeeded`는 평가 처리가 끝났다는 뜻이며 규칙 통과와 다르다. 따라서 업무 회귀는 처리 완료 상태에서도 `block`이다.

같은 평가 코어로 기록 응답을 재현하고 정상·회귀·누락의 기준 비교도 확인한다. 명령의 `status: passed`와 종료 코드 0은 시연의 기대 결과를 확인했다는 뜻이다. 회귀와 누락이 차단되는 것도 시연의 성공 조건이다. 이 명령은 관리자 승인·실제 인증·서명 게이트·배포를 수행하지 않으며 모든 결과의 `deploymentAllowed`는 false다. 기록 응답의 실제 출처를 인증하지 않는다.

## 2. 평가에서 승인·반려까지 실제 로컬 API로 확인한다

[설치와 시연](portfolio-demo.md)의 준비 절차를 따라 Docker API·DB·워커를 실행한다. 기존 설치의 비밀과 기록은 보존한다. 먼저 선택 조직의 읽기 전용 준비 점검을 하고 비교 시연을 한 번 실행한다.

```powershell
npm.cmd run demo:preflight -- --organization-index 0
npm.cmd run demo:portfolio -- --compare --organization-index 0 --export-receipts
```

비교 시연은 새 합성 평가 여섯 개와 검토·감사·게이트 기록을 저장한다. 완료 출력의 후보 UUID와 같은 단계의 기준 UUID를 사용한다. 평가 통과 → 승인 대기 차단 → 관리자 승인 후 허용 → 관리자 반려 후 차단을 확인한다. 시연은 반려 상태로 끝나므로 과거 승인 시점의 서명 기록과 현재 판단을 구분한다. 결과 유효 시간이 지나면 실제 배포 판단에 과거 시연 결과를 재사용하지 않는다.

보관 공간이 부족하면 시연이 차단된다. 기존 기록을 삭제하거나 한도를 늘리지 않는다. 기존 다른 조직을 선택할 때도 해당 조직의 공간과 권한을 먼저 확인한다. [합성 수용 기준](acceptance-walkthrough.md)에서는 직접 편집한 기준의 준비 점검·등록·평가를 확인할 수 있다.

## 3. 세 화면으로 설명한다

1. 평가 근거: 후보와 기준의 고정 버전·사례·규칙을 확인하고 회귀 원인을 보여준다.
2. 비교와 검토: 비교 기준 통과, 관리자 승인 필요, 최신 승인·반려 이력을 구분한다.
3. 최종 게이트: 현재 권한·근거·유효 시간·검토를 다시 확인하고 서명된 기록을 저장한다.

아래는 실제 **v0.166** 소스 Docker API에 자체 읽기 전용 프로젝트 세션으로 연결해 촬영한 화면이다. 비교 기준 통과와 관리자 승인 필요를 구분하며 현재 배포 허용을 표시하지 않는다. 등록·평가 생성 없는 확인이며 직접 브라우저 로그인 검증은 포함하지 않는다.

![v0.166 비교 기준 통과와 관리자 승인 필요](evidence/comparison-scope-v166.jpg)

v0.169에서는 저장된 과거 기록의 비교 통과와 관리자 반려를 함께 설명한다. 아래 화면은 기존 기록을 읽은 결과이며 현재 릴리스 허용을 뜻하지 않는다. 일치하는 본문 해시가 있어도 판정·사유·비교가 모순되면 상세 설명을 거부한다.

[8분 발표 구성](portfolio-demo.md#8분-발표-구성)과 [기술 설명](portfolio-engineering.md)에서 화면 설명과 구현 근거를 확인한다. 예전 버전의 화면은 촬영 버전을 표시한 역사 자료다.

## 4. CI와 수동 배포 준비를 확인한다

[완료 범위](portfolio-status.md)는 실제 소스 커밋·CI·이미지 digest와 검증 범위를 연결한다. 워크플로는 소스 검사 → 후보 이미지 발행 → 별도 runner의 정확한 digest 실행 → 검증한 이미지 승격 순서다. 태그 대신 검증한 digest를 지정한다.

[이미지 전달과 수동 배포 절차](github-delivery.md)는 별도 호스트의 준비·백업·마이그레이션 일치·읽기 전용 사전 점검·이미지 교체·복귀 조건을 설명한다. 현재 배포 서버는 없다. 이 문서의 절차가 실제 서버 배포 완료를 뜻하지 않는다.

## 포트폴리오의 완료 조건

- 다섯 합성 평가 결과와 회귀·누락 비교를 오프라인 명령으로 확인한다.
- 실제 로컬 API에서 평가 근거·승인 대기·승인·반려·서명 게이트를 재현한다.
- 같은 커밋의 원격 CI와 정확한 이미지 검증 출처를 확인한다.
- 설치·시연·수동 배포 준비·복원 절차와 남은 고객 연동 범위를 설명한다.

고정 가중치를 정하지 않았으므로 이 체크리스트를 수치 진행률로 환산하지 않는다. 기능·로컬 검증·CI 전달과 실제 고객 운영을 각각의 완료 범위로 판단한다.

## 서명된 과거 기록의 오프라인 검사

내보낸 서명 기록과 별도 경로로 신뢰한 공개키를 준비한 뒤 `npm.cmd run receipt:inspect -- receipt.json trusted-public.pem`을 실행한다. 사유·변경·회귀 개수와 과거 승인 상태를 출력하며 현재 배포는 허용하지 않는다. 조직·프로젝트·실행 기대값 옵션을 사용하면 다른 범위의 유효한 서명도 거부한다. [사용법과 확인 범위](receipt-signatures.md#과거-판정의-오프라인-설명-v0170)를 참고한다. 기대값은 검사 대상 기록을 그대로 복사하지 않고 사전에 선택한 범위에서 가져온다.
