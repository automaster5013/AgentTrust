# 프로젝트 CI 자격증명과 검증 기록 — v0.4

관리자는 화면의 ‘프로젝트 CI 접근 키’에서 프로젝트·키 이름·유효 시간(60초~30일)을 선택해 발급한다. 원문은 발급 응답에서 한 번만 제공한다. 목록·DB·감사 기록은 키 원문을 보존하지 않는다. 화면에서는 마스킹하고 닫기·로그아웃 시 메모리의 입력값을 지운다. 키 복사 이후 운영체제 클립보드 보존은 사용자가 관리한다.

`POST /v1/ci-credentials`: `{ name, projectId, ttlSeconds }`, 관리자 세션 필요. `GET /v1/ci-credentials`는 관리자에게 메타데이터만 반환한다. `POST /v1/ci-credentials/:id/revoke`는 반복 요청에도 감사 이벤트를 중복하지 않는다. 발급자 관리자 멤버십이 비활성화되거나 관리자 역할을 잃으면 해당 키도 인증되지 않는다.

CI 키는 `atci_` 접두어와 256비트 무작위 비밀로 구성하고 SHA-256만 DB에 저장한다. 키는 하나의 조직·프로젝트에 고정된다. `Authorization: Bearer <key>`로 `POST /v1/release-gate`만 호출할 수 있다. 카탈로그·실행 근거·사용자 정보·키 관리·감사 목록 등 다른 보호 경로는 거절한다. 키를 CI secret으로 주입하고 명령 인수·저장소·로그에 넣지 않는다. 기존 로컬 조회자 키를 쓰는 CLI 호환 경로도 유지하지만, CI에는 범위가 좁은 전용 키를 사용한다.

`npm run release:gate`의 환경변수는 release-integration.md를 따른다. CLI는 서버의 판정과 아티팩트, 요청 버전/실행 ID 일치와 해시를 확인한다. 오류는 종료 코드 2, 차단은 1, 검증 통과는 0이다. JSON 출력에는 키나 원문 평가 응답이 없다. 출력물을 파이프라인 아티팩트로 저장할 수 있다. 0을 확인한 다음에만 별도의 배포 작업을 진행한다.

판정은 DB 시간과 프로젝트 범위의 불변 실행을 사용한다. 키를 트랜잭션 안에서 재확인하고 잠가, 철회와 검증을 순서대로 처리한다. 이미 진행 중인 검증은 완료될 수 있으며 이후 요청은 거절된다. 기대 버전 오류·유효 시간 초과·증거 누락·회귀는 차단한다.

통과와 차단은 `release_receipts`에 append-only로 저장하며 `ci.release.checked` 감사 이벤트에 연결한다. 아티팩트는 요청, 판정, 조직/프로젝트, 확인 시간, 후보/기준 실행의 스냅샷·결과 해시와 자체 해시를 포함한다. 일반 세션은 자신의 프로젝트에서 `GET /v1/release-receipts`와 `GET /v1/release-receipts/:id`로 조회·JSON 저장할 수 있다. 조회 시 DB에 저장된 해시를 다시 검증한다.

아티팩트 해시는 변조·손상 확인용이며 공개 키 서명이 아니다. 파일만으로 신뢰할 수 있는 배포 승인을 증명하지 않는다. 저장한 기록은 과거 검증의 근거이고 재사용 가능한 배포 권한이 아니다. 배포 직전 새로 게이트를 확인해야 한다. 원격 runner 연결·OIDC·서명 키와 승인 보존 정책은 후속 단계다.

인증 전 조직 식별은 제한된 DB 함수 하나로 수행한다. PUBLIC 실행 권한을 철회하고 고정 search_path와 완전한 테이블 이름을 사용한다. [PostgreSQL SECURITY DEFINER 지침](https://www.postgresql.org/docs/current/sql-createfunction.html)을 따른다. 조직 RLS와 프로젝트 조건은 저장·조회 경로에 적용한다.
