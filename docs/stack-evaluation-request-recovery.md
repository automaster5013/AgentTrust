# 단일 평가 요청의 불확실한 응답과 복구

평가 생성·검토·취소는 저장 요청과 그 뒤의 현재 게이트 조회를 구분한다. 응답 유실·10초 시간 제한·잘못된 JSON/UTF-8·1 MiB 초과 응답·서버/게이트웨이 5xx는 저장되지 않았다고 단정하지 않는다. 고정 안내를 표시하며 임의 응답 본문이나 오류를 화면에 출력하지 않는다. 명시적 400/401/403/404/409/413/422/429 거부와, 올바른 저장 응답을 확인한 뒤 조회만 실패한 상태를 별도로 표시한다.

평가 생성은 원래 시나리오·공급자·관리자 검토 조건과 요청 키를 현재 화면의 메모리에 보관한다. 응답이 불확실하면 새 평가 제출을 잠시 막고 두 명시적 행동을 제공한다. **평가 요청 결과 다시 조회**는 저장 여부를 읽기 전용으로 확인한다. **같은 평가 요청 다시 제출**은 편집한 양식 대신 원래 입력과 같은 키를 사용한다. 이미 저장된 요청이면 서버의 기존 멱등 admission을 반환하므로 추가 평가나 공급자 호출을 만들지 않는다. 자동 쓰기 재시도는 없다. 화면을 닫거나 로그인 사용자·조직·프로젝트가 바뀌면 이 메모리 정보는 사라지며 서버의 처리가 취소되는 것은 아니다. 최근 평가 목록에서 실제 결과를 확인한다.

`GET /api/run-requests/{key}`는 기존 `stack_runs`를 현재 조직·프로젝트·요청자와 정확한 키로 조회한다. ASCII 키는 8~100자로 제한하고, 다른 요청자나 조직·없는 키는 404다. 조회자도 자신의 과거 요청은 읽을 수 있다. 프록시와 Gateway에는 이 GET만 추가하며 POST를 허용하지 않는다. 응답은 요청 키·조직·프로젝트·요청자·평가 ID와 `deploymentAuthority:false`만 반환한다. 키는 권한이나 인증 비밀이 아니다. 해당 순간의 404는 진행 중인 원래 요청의 미저장을 확정하지 않는다.

화면은 조회 프레임의 정확한 필드·키·소유 범위와 실제 평가의 ID·원래 입력을 대조한 후 근거를 연다. 저장 응답이 확인되면 현재 게이트와 목록을 별도로 읽는다. 게이트를 확인하지 못하면 배포 허용을 표시하지 않으며 저장 확인과 조회 실패를 구분한다. 검토 응답은 정확한 ID/결정 필드와 제출한 문자열 결정을 확인한다. 취소 응답은 선택 평가의 범위·시나리오·공급자·검토 조건과 취소 결과 계약을 확인한다. 모든 Workspace JSON 요청은 실제 UTF-8 바이트 한도 1 MiB와 10초 제한을 사용한다.

실제 기존 소유 요청의 조회·다른 요청자/조직·없는 키·익명·허용하지 않은 메서드는 `scripts/stack-evaluation-request-resolution-smoke.py`로 검사한다. 기존 요청 키는 메모리에서 대조하며 보고서에 기록하지 않는다. 소스와 정확한 registry CI 경로에 포함한다. 브라우저의 응답 유실·같은 키 재제출·치환/503 복구·검토/취소 경계는 명시적 합성 응답과 가로챈 POST를 사용하며 로컬 업무 기록이나 공급자 호출을 새로 만들지 않는다. 원격 전달 및 실제 운영 배포 준비는 정확한 리비전의 결과로 별도 확인한다.

로컬 검증: Java 142개(소유 요청 조회 6개 포함), Console 115개 및 타입 검사, Core/Gateway/Console 후보 빌드가 통과했다. 실제 기존 요청의 읽기 전용 API 8개 검사와 브라우저 11개(새 쓰기 복구 4개·검토 이력 3개·기존 근거/읽기 시간 제한 4개)가 통과했다. 새 브라우저 검사는 모든 평가 생성·검토·취소 POST를 가로채 전달하지 않았고 합성 응답을 실제 범위의 조회 결과와 구분했다. 세 서비스 적용 전후 업무 테이블 18개와 다른 컨테이너 17개, 마지막 Console 보정 전후 다른 컨테이너 19개는 동일했다. 새 데이터·유료 공급자 호출·운영 배포는 수행하지 않았다. 정확한 리비전의 원격 CI·게시 이미지·서명 전달 결과는 별도로 확인한다.
