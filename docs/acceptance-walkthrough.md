# 합성 수용 기준으로 평가와 릴리스 승인 재현하기

기업 개발팀의 관리자와 개발자가 같은 고정 기준으로 변경을 평가하고 승인·반려 이후의 릴리스 판단을 확인하는 절차다. 공개 합성 사례와 모의 응답만 사용한다. 실제 고객 연결이나 운영 서버 배포는 포함하지 않는다.

## 기준을 먼저 점검한다

```powershell
Set-Location C:\AgentTrust
npm.cmd run acceptance:check
```

Docker와 접근 키 없이 공개 프로필의 두 사례·다섯 규칙을 검사한다. 정상 응답은 pass, 업무 회귀·금지 도구 호출은 block, 증거 누락·실행 오류는 inconclusive로 구분돼야 한다. 정책은 최소 통과율 100%와 관리자 승인을 요구한다. 결과는 원문이나 이름을 출력하지 않는다.

사용자 프로필을 점검할 때는 `node scripts/check-acceptance-profile.mjs --profile <로컬-UTF-8-JSON>`을 사용한다. 사용자 파일은 64 KiB 이하이며 이 도구는 로그인·버전 등록·평가 생성·릴리스 승인을 수행하지 않는다.

## 화면에서 기준 초안을 준비한다

로컬 API와 워커를 실행하고 관리자 키로 로그인한다. **합성 데이터셋 등록 → 합성 수용 기준 초안 준비**를 누르면 데이터셋 JSON과 관리자 승인 정책 양식이 함께 채워진다. 승인 유효 시간은 600초다. 준비 중 편집한 내용이나 바뀐 프로젝트는 이전 응답이 덮어쓰지 않는다.

초안을 편집한 뒤 **현재 합성 초안 준비 점검**을 누른다. 현재 프로젝트의 에이전트 다섯 개·기준 재사용·평가 여섯 개를 위한 보관 공간·동시 슬롯·신규 버전 필요 수를 읽기 전용으로 확인한다. 입력 해시와 프로젝트가 다른 응답은 표시하지 않는다. 초안 수정이나 30초 경과 시 결과를 지우므로 필요한 시점에 다시 점검한다. 점검은 등록·평가·승인을 실행하거나 용량을 예약하지 않는다.

각 양식의 **새 데이터셋 버전 등록**과 **새 정책 버전 등록**을 명시적으로 실행한 뒤 평가 설정에서 사용할 버전을 선택한다. 기존 등록 버전을 정확히 재사용하려면 새로 등록하지 않고 기존 목록에서 선택한다. 초안 준비는 기존 선택을 바꾸지 않는다. 관리자 운영 상태의 조직 전체 등록 버전 용량은 관측값이며 실제 등록에서 한도를 다시 검사한다.

정상 모의 에이전트로 평가하고 사례별 근거를 확인한다. 평가 pass여도 관리자 승인이 없으면 최종 게이트는 차단된다. 근거 승인 후 새 게이트를 확인하면 조건 충족 시 허용 기록이 생성되고, 이후 반려하고 다시 확인하면 차단 기록이 생성된다. 이미 저장한 허용 기록이 현재 배포 권한을 보장하지 않는다.

## 같은 흐름을 CLI에서 재현하고 독립 검증한다

```powershell
npm.cmd run demo:acceptance -- --organization-index 1 --plan-only
npm.cmd run demo:acceptance -- --organization-index 1 --export-evidence
```

`--plan-only`는 서명 키와 업무 데이터 생성 없이 전체 계획을 확인하고 자체 세션을 종료한다. 새 버전 필요 수와 기준 재사용·모의 에이전트 버전을 GET으로 확인한다. 결과는 용량 예약이 아니므로 실제 시연에서 다시 검증한다.

선택한 기존 조직의 관리자·프로젝트 범위, 워커 신호, 실행 여섯 개의 보관 용량과 활성 슬롯을 확인한다. 기준의 이름·내용 해시를 정확히 재사용하거나 필요한 새 버전 0~2개를 등록할 수 있는지 확인한다. 실제 등록된 기준은 고정 ID·종류·내용 해시를 조회해 다시 검증한다.

기준 실행 하나와 다섯 후보 실행, 승인·반려 이후 비교 게이트의 서명 기록 일곱 개를 검사한다. 시연 종료 시 정상 후보도 반려 상태로 두고 자체 실행·세션만 정리한다. 성공 결과의 evidenceBundle은 새 비공개 디렉터리와 manifest SHA-256을 가리킨다.

```powershell
node scripts/verify-acceptance-evidence.mjs <새-묶음-디렉터리> <신뢰-공개키-파일> <외부에서-보관한-SHA-256>
```

검증자는 동일 출처의 manifest만 신뢰하지 않고 별도로 보관한 해시와 신뢰 공개키를 제공한다. 프로필과 실행 여섯 개·기록 일곱 개·검토 두 개의 결합, 규칙·요약·내용 해시와 서명을 검증한다. 묶음에는 합성 입력·출력·규칙과 검토 의견 원문이 들어 있으므로 비공개 `.local`에서 보관한다. 검증 성공은 과거 증거의 일치이며 현재 배포 허용은 새 최종 게이트에서 확인한다.

## CI 이미지 전달과 수동 배포 준비

GitHub CI는 소스 테스트 후 후보 digest를 발행하고 별도 작업에서 같은 이미지를 실행해 검증한 뒤 승격한다. [전달 절차](github-delivery.md)의 manifest·checksum·revision·workflow·digest 대조를 따른다. 현재 배포 대상 서버는 없으며 Docker 이미지와 수동 배포 준비까지 확인한다. 로컬 재현 결과나 과거 서명 기록을 고객 운영 성과로 소개하지 않는다.
