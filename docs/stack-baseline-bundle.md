# 비교 기준까지 포함하는 오프라인 증거 번들

2026-10-12 KST 로컬 서비스 적용과 실제 API·브라우저 검증을 완료했다. GitHub CI와 정확한 게시 이미지·전달 서명 검증은 해당 revision의 별도 실행 결과로 확인한다.

기준이 지정된 새 과거 판정은 schema v3로 후보 캠페인과 기준 캠페인의 부모·자식 해시, 바이트 수 및 MinIO 저장 버전을 모두 Java Ed25519 서명에 묶는다. 조건 자체도 기존 schema v2와 동일하게 서명한다. 기존 v1/v2 판정과 기존 보관 바이트는 변경하지 않는다. 멱등 재요청은 이전에 발급한 원래 서명을 반환한다.

`GET /api/campaigns/{campaign}/receipts/{receipt}/bundle`은 schema v3 판정에 한해 schema v2 번들을 반환한다. 후보의 기존 `campaign`, `parent`, `children`과 함께 `baseline`에 기준의 동일한 세 항목을 포함한다. 기준 ID·조직·프로젝트·에이전트 버전·해시·동일 데이터셋과 실제 생성 시각·평가 상태를 조건과 대조한다. Java는 인증 범위와 기존 서명을 확인한 후 보관본을 읽고, 정확한 원래 저장 버전·해시가 서명과 다르면 번들을 발급하지 않는다. 기존 v1/v2 판정의 번들은 schema v1을 유지한다.

TypeScript와 독립 공개키 CLI는 양쪽 부모의 실제 바이트와 불변 버전을 검증한 뒤 모든 자식 보관 바이트를 검증한다. 사례 결과에서 필수 회귀·미확인·개선을 다시 계산하여 서명에 기록된 비교와 대조한다. 새 판정에서 기준 바이트를 빼고 이전 번들로 위장하는 것도 거부한다. 브라우저는 모든 검증이 끝난 뒤에만 파일을 만든다. 최대 512KiB 번들과 16KiB 서명 payload 제한은 확대하지 않는다.

과거 HTML은 양쪽 보관 바이트를 실제 검증한 경우에만 기준 보관본과 실제 비교 검증을 표시한다. 이전 v2 판정은 기준 ID·조건만 서명 검증하고 별도 기준 바이트가 없다는 안내를 유지한다. HTML 자체는 서명된 문서가 아니며 원본 번들과 별도로 신뢰한 공개키로 검증해야 한다. 모든 판정과 번들의 `currentDeploymentAuthority`는 false다.

코드 검사에서는 Java 102개, TypeScript 81개, 정적 HTML 보고서 5개가 통과했다. 새 검사는 실제 Ed25519 서명을 사용해 기준 바이트 누락·치환·저장 버전 변경·사례 중복·범위 변경·서명된 비교와 실제 사례의 모순을 거부한다. 실제 기준 게이트 검사 6개 묶음과 취소된 기준 검사 2개 묶음도 통과했다. `stack-baseline-bundle-smoke.py`는 자연 만료와 취소된 기준 각각에서 실제 Java 서명과 양쪽 보관 바이트를 검증하고 오프라인 거부 검사 6개씩을 통과했다. 다른 조직의 조회와 조회자 역할의 판정 발급도 거부됐다.

전체 브라우저 22개 검사가 통과했다. 관리자의 실제 Python 평가·승인·v3 판정 발급·양쪽 근거 번들 다운로드와, 변경된 기준 자식을 두 번째 다운로드 전에 거부하는 흐름을 확인했다. 취소된 평가의 유사 근거 버튼은 비활성화되고 검색 대상이 아니라는 안내가 표시됐다. 첫 실행은 브라우저 실행 파일 누락으로 화면 검증 전에 실패했으며, 프로젝트 전용 headless Chromium 설치 후 전체 검증을 다시 수행했다. [Windows 재현 절차](stack-reviewer-guide.md#windows-개발-호스트의-브라우저-검증)를 참고한다.

적용 전에 [3시간 읽기와 2시간 서명 관찰](stack-readonly-soak.md)을 완료했고, 명시적으로 API·콘솔 두 서비스만 업데이트했다. 실행 이미지 ID는 준비한 이미지와 일치했고 적용 전후 업무 테이블 16개가 동일했으며 롤백 이미지 2개를 보존했다. 검증 후 창 시작 이전 새 스택 테이블 14개, 기존 JavaScript 테이블 11개와 감사 67,911건, 비공개 파일·설정·기존 SQL 및 정지된 LogiTrack 자산의 보존을 확인했다. 이 결과는 새 번들의 장시간 관찰이나 운영 배포·고객 SLA를 증명하지 않는다.

같은 후보의 특징 색인은 한 묶음의 영구 실패가 다음 정상 결과를 막지 않게 조직별 완료 시각·ID 경계를 순회한다. 한 번에 최대 20개를 처리하고 끝에 도달하면 이전 실패를 재시도한다. 경계는 메모리에만 보관하며 재시작 후 다시 순회한다. 정밀 시각·동일 시각 ID 순서를 유지하는 실제 스케줄러 회귀 검사는 거부 항목 20개 뒤의 정상 결과와 이후 거부 항목 재시도를 확인했다. 기존 결과·DB 스키마는 변경하지 않는다.
