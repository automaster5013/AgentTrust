# 기록된 합성 출력의 문자열 규칙 평가 — 구현 전 계약

2026-11-12 소스 조사 당시의 계약이며 이후 [제한 범위 소스 구현과 로컬 검사](stack-recorded-text-rules.md)를 완료했다. 합성 후보 수용·운영 적용은 아직 완료하지 않았다. 첫 범위는 사용자가 기록한 합성 출력에 `contains`와 `not_contains`를 적용하는 등록→캠페인 실행→규칙별 근거 조회다. 4310의 도구 이벤트·JSON Schema·관리자 정책·범용 connector 전체 이전은 별도 미완료다.

## 기존 저장소와 실행 경계

V10의 불변 버전 저장소는 에이전트 정의 4096바이트, 데이터셋 정의 8192바이트를 허용한다. 사례 인덱스는 0~7이다. V13의 실행 시나리오 CHECK는 `pass`, `block`, `missing_evidence`, `error`, `quality`만 허용한다. 새 `recorded-output` 시나리오를 추가하는 방식은 DB 마이그레이션을 요구하므로 현재 범위에서 사용하지 않는다.

검토할 구현 경로는 기존 `quality` 분류 안에 **새 불변 계약 `recorded-text-rules-v1`**을 명시하는 것이다. 기존 `reference-answer-v1`이나 고정 시나리오를 새 의미로 해석하지 않는다. 공개 단일 실행 POST가 허용하는 고정 시나리오는 유지하고, 새 계약의 실행은 검증된 에이전트·데이터셋 쌍을 선택한 캠페인에서만 허용한다. provider는 기존 `synthetic`이며 외부 모델·URL·예약 API 호출을 하지 않는다. 화면에는 참조 답안 평가와 구분해 기록된 합성 출력 평가임을 표시해야 한다.

`VersionController`/`VersionRegistry`에 새 모드를 추가할 때 기존 DTO와 파서를 느슨하게 만들지 않는다. 새 사례의 input/output/rules는 별도 엄격한 타입·필드 목록으로 검증한다. `CampaignService`는 두 버전의 계약이 정확히 일치하는지 확인하고 기존 RLS·역할·CSRF·불변 좌표·동일 내용 재확인/다른 내용409를 유지한다.

## 실행 및 완료 결합

`RunService.job`은 저장된 부모·에이전트·데이터셋 해시와 사례 인덱스/ID/필수 여부를 확인한 후 새 `recordedCase`와 전용 실행 프로필 해시를 만든다. 기존 `qualityCase`와 동시에 존재하거나 서로 다른 계약이 섞이면 거부한다. 완료 callback에서 원래 저장된 전체 사례와 정확히 재결합하고, 선언된 규칙 ID·필수 여부·순서·개수와 결과를 대조해야 한다. 단순히 작업자가 보낸 총 판정만 믿지 않는다.

`QueuePublisher`는 검증된 새 작업을 별도 subject/consumer로 보낸다. 기존 고정·참조 작업의 subject와 소비자를 유지한다. 새 worker는 기록된 문자열만 평가하고 provider 예약·외부 연결을 하지 않는다. 기존 작업자 인증과 완료 endpoint를 재사용한다. 기존 해시 대상인 `app.py`, `execution_profiles.py`, `quality_*` 평가 소스를 수정해 과거 실행 프로필을 바꾸는 방법을 피하고, 별도 모듈·프로필 및 lifespan 합성으로 연결한다. 컨테이너 진입점과 readiness에도 새 소비자의 실패를 반영하되 기존 두 소비자의 성공을 대체하지 않는다. 이 변경은 소스 및 합성 후보에만 적용하며 현재 복구 서비스에는 적용하지 않는다.

## 첫 구현 한도와 의미

- 최대 2사례, 사례당 최대 4규칙. 사례·규칙 ID는 유일하며 필수 사례와 필수 규칙이 존재해야 한다.
- input/output은 각각 UTF-8 최대 512바이트, 규칙 value는 최대 64바이트. 잘못된 surrogate·NUL·빈 규칙 값과 알 수 없는 필드는 거부한다.
- 정규화한 개별 사례 최대 2048바이트, 데이터셋 최대 4096바이트를 함께 적용한다. 실제 전체 작업 JSON도 기존 4096바이트를 초과하면 게시하지 않는다. JSON escaping으로 늘어난 바이트를 별도로 확인한다.
- 문자열 비교는 대소문자 구분·원래 Unicode 문자열의 부분 포함이다. 정규식·코드·공백 제거·Unicode 정규화·외부 참조를 추가하지 않는다. 빈 output은 기록된 빈 문자열로 평가하고 누락된 output과 구분한다.
- 필수 규칙 실패는 block, 실행 오류나 필수 근거 누락은 inconclusive다. 선택 규칙 실패는 해당 규칙 근거에 표시한다. 결과 reason은 규칙 종류와 통과 여부만 포함해 원문 input/output/value를 복제하지 않는다.
- 작업의 기존 120초 완료 기한을 유지하고 새 로컬 문자열 평가에는 짧은 제한 시간을 적용한다. 취소·지연 완료·중복 완료의 기존 동작을 보존한다.

정확한 한도는 구현 검사에서 실제 JSON·부모 보관 번들 16KiB와 함께 확인해야 한다. 한도를 늘리거나 기존 검증을 약화해 통과시키지 않는다.

## 수용 조건

등록만 가능한 버전으로 완료 처리하지 않는다. 실제 합성 후보의 명시 등록→NATS→Python→기존 완료 API→캠페인 사례 상세까지 확인한다. 통과·필수 실패·선택 실패·빈 출력·다국어와 바이트 경계, 잘못된 규칙·원문/해시/부모/사례/프로필 치환·계약 혼합·늦은 완료를 검증한다. 조회자 등록/실행403과 익명401, scope 경계, 초안 보존·scope/role 변경 제거, 모바일, 기존 계약 회귀를 포함한다.

기존 사례 근거 UI와 서명/보관 검증 파서는 새 계약을 명시적으로 지원해야 한다. 지원하지 않는 서명 경로를 자동 실행하거나 기존 계약으로 위장하지 않는다. 실제 서명 발급의 새 기능 이전 및 운영 신뢰 수립은 별도 범위다. DB migration·인증 설정·정책 권한 확대가 필요하다는 증거가 생기면 그 부분은 설계 대기로 남긴다.
