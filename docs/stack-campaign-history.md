# 조직별 캠페인 이력과 이전 비교 기준

최근 50개 캠페인 목록과 별도로 전체 보관 캠페인을 25개 keyset 페이지로 탐색한다. Java는 로그인한 조직·프로젝트의 RLS 트랜잭션에서 조회하며 `created_at DESC, id DESC` 순서를 유지한다. 기존 범위 인덱스와 200개 보관 한도를 사용하므로 새 데이터 테이블이나 마이그레이션은 추가하지 않는다.

읽기 경로는 다음과 같다.

- `GET /api/campaign-history`
- `GET /api/campaign-history/page/{cursor}`
- `GET /api/campaign-history/dataset/{datasetVersionId}`
- `GET /api/campaign-history/dataset/{datasetVersionId}/page/{cursor}`

107자 커서는 `CMP` 도메인, 조직·프로젝트, 데이터셋 필터 유무와 UUID, DB의 정확한 마이크로초 시각과 마지막 행 UUID를 포함한다. 다른 조직·프로젝트 또는 다른 필터에서 재사용하면 400이다. 이 값은 탐색 경계이며 서명이나 권한 토큰이 아니다. 데이터셋 필터는 현재 조직의 행만 조회하며 외부 데이터셋에는 빈 페이지를 반환한다. 임의 조직 선택 쿼리와 쓰기 경로는 Gateway/BFF에서 거부한다.

Next.js의 **프로젝트 캠페인 이력**에서 이전 캠페인의 고정 버전과 근거를 열 수 있다. 캠페인을 열면 같은 데이터셋 버전으로 필터가 바뀐다. 이전 행의 **비교 기준 선택**은 회귀 비교 폼에 기준 ID를 넣는다. 최근 목록에 없는 캠페인도 선택할 수 있다. 비교 실행 시 Java가 완료 상태·같은 에이전트 이름·같은 데이터셋 버전과 내용 해시를 다시 확인한다. 기준을 선택한 것만으로 비교 성공이나 릴리스 권한을 표시하지 않는다.

브라우저는 응답 범위, 정확한 필드, 순서·중복·최대 25개, 요청한 페이지 경계와 다음 커서의 마지막 행 결합을 검증한다. 범위/필터가 바뀌면 탐색을 초기화하며 종료된 요청을 취소한다. 10초 기한과 100페이지 메모리 한도를 적용하고 오류에는 이전 표를 지운다. 이력에는 저장된 요청 메타데이터만 포함한다. 완료 결과·보관 증거·현재 게이트는 선택 후 각 기존 검증 경로에서 조회한다.

`scripts/stack-campaign-history-smoke.py`는 기존 행만 읽어 모든 페이지를 PostgreSQL 정렬과 TypeScript 검증기에 대조하고, 조회자·외부 조직·필터 변경·잘못된 커서를 검사한다. 평가나 모델 호출을 생성하지 않는다. 실제 브라우저 검사는 기존 캠페인 근거 열기와 이전 시연에서 생성한 기준/후보의 실제 회귀 비교를 수행한다.


2026-10-11 로컬 검사에서 기존 105개 캠페인·5페이지를 대조하고 API 경계 검사 4개를 통과했다. 실제 브라우저의 캠페인 이력/기준 선택 2개와 기존 평가 이력/사용량 회귀 2개도 통과했다. TypeScript 49개·Java 74개·Gateway 19개와 Docker 빌드가 통과했고, 실제 세 서비스 적용 전후 public 업무 테이블 15개의 행 수와 해시가 동일했다. 최신 커밋의 전체 전달 CI는 별도 결과로 확인한다.
