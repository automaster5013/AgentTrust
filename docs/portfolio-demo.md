# AgentTrust 포트폴리오 시연

기업 개발팀이 에이전트 변경을 평가하고, 근거와 관리자 검토를 바탕으로 릴리스 여부를 판단하는 합성 시연이다. 실제 모델·고객 데이터·배포 서버를 사용하지 않는다.

## 준비와 실행

Node.js 24와 Docker Desktop을 준비하고 저장소 루트에서 실행한다. 기존 설치는 setup이 보존하는 접근 키·서명 키와 DB를 사용한다. `.env`와 `.local`은 공개하거나 업로드하지 않는다.

```powershell
npm.cmd ci --cache .cache/npm --ignore-scripts
npm.cmd run setup
npm.cmd run docker:up
npm.cmd run demo:preflight
npm.cmd run demo:portfolio
```

Linux에서는 `npm.cmd` 대신 `npm`을 사용한다. 기본 API는 `http://127.0.0.1:4310`이며 PORT 설정만 지원한다. 외부 주소는 받지 않으며 `--compare`와 `--export-receipts`를 각각 한 번 선택적으로 받는다. seeded 프로젝트의 합성 데이터셋과 모의 에이전트, 기본 정책이 필요하다. 실제 작업 루트는 `C:\AgentTrust`다. LogiTrack 리소스는 변경하지 않는다.

## 확인할 흐름

| 단계 | 평가 결과 | 최종 게이트 | 시연할 의미 |
|---|---|---|---|
| 정상 응답 | pass | 허용 | 고정된 버전과 완전한 근거가 기준을 충족 |
| 업무 회귀 | block | 차단 | 필수 규칙 실패는 릴리스 불가 |
| 증거 누락 | inconclusive | 차단 | 판단 불가를 통과로 처리하지 않음 |
| 관리자 검토 정책의 정상 응답 | pass | 승인 대기·차단 | 평가 통과와 관리자 승인은 별도 |
| 관리자 승인 후 | pass | 허용 | 현재 유효한 승인과 근거를 함께 검사 |
| 관리자 반려 후 | pass | 차단 | 과거 통과 기록이 현재 배포 권한이 되지 않음 |

명령은 평가 4개, 최종 게이트 확인 6개를 실행하고 모든 게이트 기록의 Ed25519 서명을 로컬 신뢰 공개키로 검증한다. 단계별 JSON에는 실행 ID·판정·검증 기록 ID가 포함된다. 마지막 출력의 `status: passed`와 프로세스 종료 코드 0을 함께 확인한다. 실패하면 `blocked`, 종료 코드 1이며 원문 오류나 접근 키를 출력하지 않는다.

## 기준 실행 비교까지 자동으로 준비하기 — v0.113

```powershell
npm.cmd run demo:portfolio -- --compare
```

기본 시연과 같은 합성 사례에 두 기준 실행을 추가한다. 기본 정책과 관리자 정책별로 서로 다른 정상 응답 기준을 만들고, 후보 4개·기준 2개 평가와 최종 게이트 6개의 총 12단계를 수행한다. 정상 비교는 통과, 업무 회귀는 회귀 규칙 포함 차단, 근거 누락은 비교 미완료·차단이다. 관리자 사례는 비교가 통과해도 승인 대기·반려이면 차단되고 승인 후에만 허용된다.

출력의 각 게이트에는 후보 `runId`, 정책에 맞는 `baselineRunId`, 비교 가능 여부·통과 여부·회귀 수가 포함된다. 후보의 고정 버전과 후보·기준의 실행·스냅샷·결과 해시를 원본 artifact와 대조하고 로컬 신뢰 공개키로 서명을 검증한다. 마지막 출력의 `withBaselineComparison: true`, `steps: 12`, `status: passed`와 종료 코드 0을 함께 확인한다. 추가 인자·중복 옵션은 인증 전에 거절한다. 실패 정리와 자체 세션 종료는 기본 시연과 같으며 기존 기록을 삭제하지 않는다.

화면에서 출력한 후보 UUID를 조회하고 ‘기준 실행과의 회귀 비교 포함’을 선택한 뒤 해당 게이트의 `baselineRunId`를 입력하면 같은 비교를 새로 확인할 수 있다. 결과 유효 시간 600초가 지나면 명령을 다시 실행한다. 자동 시연은 관리자 사례를 반려로 끝내므로 승인 대기·승인 시점의 과거 서명 기록과 현재 반려를 구분한다.

## 화면 시연

1. 로컬 화면에 관리자 접근 키로 로그인한다. 키는 `.local/credentials.json`에서 로컬로 확인한다.
2. 기본 프로젝트의 실행 기록에서 ‘실행 ID로 바로 조회’에 명령이 출력한 실행 UUID를 붙여 넣고 ‘실행 ID 조회’를 누른다. 조회 완료 뒤 탐색 메뉴의 평가 근거로 이동해 스냅샷과 사례별 근거, 필수 규칙의 결과를 설명한다.
3. 탐색 메뉴의 최종 게이트로 이동해 새 검증을 요청한다. 화면의 확인 시각·검증 기록 ID와 CI 릴리스 검증 기록을 함께 확인한다. ‘이번 검증 기록 JSON 저장’으로 해당 artifact·해시·서명을 바로 내보낼 수 있다.
4. 관리자 검토 사례를 선택한 뒤 탐색 메뉴의 릴리스 검토에서 승인·반려 이력을 확인한다. 시연 명령 종료 후 이 사례는 반려 상태다. 과거 승인 시점의 통과 기록과 현재 차단을 비교한다.
5. 필요하면 새 합성 실행을 만들고 직접 승인한 뒤 최종 게이트를 확인한다. 실제 배포는 수행하지 않는다.

## 8분 발표 구성

아래 시간은 권장 발표 배분이며 측정된 성능이나 실제 데모 실행 시간이 아니다. 데모 명령과 화면 로그인은 발표 전에 준비한다. 결과가 기본 유효 시간 600초를 넘었다면 새 평가와 게이트를 실행한다.

| 시간 | 보여줄 내용 | 확인할 근거 |
|---|---|---|
| 0–1분 | 기업 개발팀의 변경 평가와 릴리스 승인 문제 | 고정 버전·근거·별도 최종 게이트 |
| 1–3분 | 정상 응답과 업무 회귀 비교 | 같은 데이터셋·정책의 후보와 기준, 변경/회귀 규칙 수 |
| 3–4분 | 회귀 규칙 링크로 정확한 사례 이동 | 선택한 사례와 전체 사례 수, 원문 출력·필수 규칙 실패 |
| 4–6분 | 관리자 정책의 비교 통과와 승인 대기·승인·반려 | 비교 판정과 최종 판단 분리, 최신 검토 이력 |
| 6–7분 | 원본 기록 저장과 신뢰 공개키 검증 | JSON은 과거 확인 기록, 서명 검증은 현재 배포 권한이 아님 |
| 7–8분 | CI의 테스트·후보 digest·독립 실행·승격 | [고정 검증 기준선](portfolio-engineering.md), 미완료 고객 연동·실제 서버 배포 |

기준은 최근 완료 목록에서 선택하거나 UUID로 입력한다. 후보 자신은 기준으로 지정할 수 없으며 목록은 호환성 검증 결과가 아니다. 관리자 정책 비교를 시연할 때에는 기준·후보 모두 같은 정책 내용을 사용한다. 반려로 끝나는 자동 데모의 관리자 사례를 그대로 사용하면 ‘승인 대기’ 대신 ‘반려’가 보인다. 승인 대기를 보여주려면 새 합성 실행을 생성한다.

회귀 링크를 누르면 기존 검색·필터를 해제하고 정확한 사례만 표시한다. ‘선택 사례 해제’로 전체 근거에 돌아오고 전체 결과 JSON의 사례 수가 유지되는 것을 설명한다. 기준 ID를 바꾸면 이전 판단·저장 버튼·회귀 링크가 무효화되는 모습도 확인할 수 있다.

## 기록과 제한

매 실행은 새 관리자 검토 정책 1개와 평가·검토·감사·게이트 기록을 추가한다. 기존 기록을 삭제하거나 덮어쓰지 않는다. 보고서는 `.local/portfolio-demo-<UUID>.json`에 독점 생성되며 합성 실행의 요약만 보관한다. 보고서 자체는 서명된 릴리스 증명이 아니며 기록 원본은 화면/API에서 조회한다. 설치된 버전이 아닌 브랜치에서 실행하는 경우 API·워커 이미지를 먼저 다시 빌드한다.

실패 시 ID를 확인한 미완료 실행을 취소하고, 승인을 시도한 사례에 반려를 추가하며 자체 로그인 세션을 종료한다. 통신 중단으로 서버가 요청을 처리했는지 알 수 없는 경우 모든 생성 기록을 발견한다고 보장하지 않는다. 정리 실패는 성공으로 처리하지 않는다. 관리자 자격증명으로 수행한 합성 시연은 실제 사람의 검토, 역할 분리, 고객 파일럿을 증명하지 않는다. 최종 게이트는 확인 시점의 판단이며 실제 배포 직전에 CI에서 다시 확인해야 한다.

## 권한과 조직 경계 시연

```powershell
npm.cmd run demo:roles
```

기존 seeded 두 조직의 접근 키를 로컬에서 사용한다. 첫 조직의 관리자·작성자·조회자와 두 번째 조직의 조회자로 자체 세션 4개를 만든다. 새 접근 키나 권한은 발급하지 않는다.

| 주체 | 검증하는 행동 | 예상 결과 |
|---|---|---|
| 작성자 | 합성 평가 생성 | 완료·평가 pass, 관리자 승인 대기 |
| 조회자 | 실행 근거와 고정 스냅샷 조회 | 200 |
| 조회자 | 평가 생성 | 403 |
| 작성자 | 정책 등록 | 403 |
| 작성자·조회자 | 관리자 승인 작성 | 각각 403, 검토 기록이 생기지 않음 |
| 다른 조직의 조회자 | 실행 조회·최종 게이트 확인 | 각각 404 |
| 관리자 | 승인·반려 기록 | 승인 후 허용, 반려 후 차단 |
| 조회자 | 승인 대기·승인·반려의 최종 게이트 | 세 판단과 서명 검증 확인 |

명령은 정책 1개·평가 1개와 검토·게이트 기록을 보존한다. 단계 11개 중 거절 검증은 6개이며 최종 게이트 서명은 3개다. 보고서는 `.local/portfolio-roles-<UUID>.json`에 독점 저장한다. 종료 코드 0과 `status: passed`, `cleanupSucceeded: true`, `sessionsLoggedOut: true`를 함께 확인한다. 권한 거절 대신 허용되거나 서명·정리가 실패하면 종료 코드 1이다. 자체 미완료 실행을 작성자로 취소하고, 승인 시도 후 실패한 사례를 관리자로 반려하며 생성한 세션을 각각 종료한다. 통신 중단의 기록 발견 제한은 앞 절과 같다.

화면에서는 역할별로 별도 브라우저 세션을 사용해 작성자의 실행 버튼, 조회자의 비활성 실행 버튼·읽기 가능한 근거, 관리자의 검토 양식을 확인할 수 있다. 이 명령은 기존 RBAC와 조직 격리를 실제 API에서 시연하며, 정책상 2인 승인이나 실사용자 역할 분리를 추가하지 않는다.

## 시연 준비 상태 점검

`npm run demo:preflight`는 데이터·정책·세션·보고서 파일을 만들지 않는 읽기 전용 검사다. Node.js 24와 PORT, 로컬 설정/두 조직의 역할 키 형식, Ed25519 키 쌍, 현재 Compose API·DB·워커 실행 상태와 API loopback 포트, 공개 health 응답의 DB 연결을 순서대로 확인한다. 첫 실패 단계 이후는 not_run으로 표시한다. status passed와 종료 코드 0, 또는 blocked와 종료 코드 1을 반환하며 고정 안내만 출력한다. 키·Docker 원문·오류 스택은 출력하지 않는다.

Docker가 꺼져 있거나 서비스가 멈췄다면 안내에 따라 Docker Desktop과 docker:up을 실행한다. 설정/키 단계가 막히면 기존 비밀 파일을 보존하고 setup 상태를 확인한다. 명령은 시작·재시작·마이그레이션·로그인·외부 연결을 수행하지 않는다. 성공은 구조와 현재 가용성의 점검이며 키의 DB 인증 유효성·seed 버전 내용·워커 실제 평가 성공·현재 이미지의 소스 일치를 증명하지 않는다. 이어서 두 데모 명령으로 실제 평가·권한·서명을 확인한다. 운영 배포 전 검사는 별도의 deploy:preflight를 따른다.

실행 ID 조회는 현재 로그인한 조직·프로젝트 권한을 그대로 적용한다. 다른 프로젝트의 실행이면 현재 프로젝트 선택을 먼저 확인한다. 없는 실행과 접근할 수 없는 실행은 상세 존재 정보를 구분해 표시하지 않는다. 목록 필터와 페이지는 유지되며 잘못된 ID를 확인하는 동안 기존 선택도 유지된다. 다른 실행 선택·프로젝트 전환·로그아웃 후 도착한 조회 응답은 선택을 바꾸지 않는다.

현재 검증 기록의 JSON은 별도 신뢰 공개키로 receipt:verify를 실행할 수 있는 기존 형식이다. [서명 운영 안내](receipt-signatures.md)를 따른다. 브라우저 다운로드는 과거 확인 기록이며 실제 배포 전에 새 게이트를 요청한다. 재검증·검토 새로고침·실행 전환 후에는 이전 다운로드가 비활성화된다. 이력에서 과거 기록을 다시 저장하는 기능은 계속 제공된다.

최종 게이트의 ‘기준 실행과의 회귀 비교 포함’을 선택하고 완료된 기준 실행 UUID를 입력하면 서버의 회귀 판단을 함께 확인한다. 같은 프로젝트 및 데이터셋·정책 내용이 필요하다. 기본값은 비교 제외이며 후보 자신은 기준으로 선택할 수 없다. 옵션·ID 변경 후 다시 확인해야 한다. 저장 파일은 선택한 기준의 원본 서명 근거를 포함한다.

## v0.50 — 최근 기준 실행 선택

최종 게이트에서 최근 완료 실행 최대 100개 중 후보 자신을 제외하고 기준 UUID를 선택한다. 목록은 호환성·통과를 보장하지 않으며 실제 게이트에서 확인한다. 직접 입력과 목록 새로고침은 입력한 UUID를 유지한다. 기준 선택은 이전 판단과 다운로드를 무효화하고 워크스페이스 변경은 목록을 비운다.

## v0.51 — 비교 판정과 관리자 승인 분리

최종 게이트에서 비교의 evaluationPassed와 전체 배포 허용을 구분한다. 관리자 검토 정책은 비교 통과와 승인 대기를 동시에 표시할 수 있다. 비교 가능 근거가 부족하면 미완료로 표시하며, 변경·회귀 규칙 수와 최대 10개 회귀 세부를 텍스트로 보여준다. 전체 근거는 원본 검증 기록 JSON에 유지한다. 서버 판단이나 승인 권한은 변경하지 않는다.

## v0.52 — 회귀 사례 근거로 이동

최종 비교의 회귀 규칙에서 후보의 정확한 사례로 이동한다. 부분 문자열 검색 대신 사례 ID를 정확히 선택하고 기존 검색·필터를 해제한다. 선택 해제 또는 검색·필터 변경으로 전체 탐색에 복귀한다. 요약·판정·원본 JSON은 전체 실행 기준을 유지한다. 이전 링크는 기준·검토·실행·워크스페이스 변경 뒤 사용할 수 없다.

## 기존 설치 재시연 기준선 — v0.82

2026-10-04의 기존 Windows 설치에서 안내한 npm ci와 setup을 다시 실행했다. .env, 역할 접근 키 파일과 서명 private/public 키 네 파일의 바이트 지문이 모두 유지됐다. 준비 5단계, 평가·승인 10단계, 권한 11단계가 통과했고 자체 세션을 종료했다. 브라우저에서도 관리자 검토 사례를 UUID로 조회한 뒤 새 최종 게이트가 반려를 이유로 차단하는 것을 확인했다. 원본 기록과 화면은 private .local에 보관한다.

이는 기존 설정의 재사용 검증이다. 로컬의 새 볼륨 설치나 다른 사용자 PC 설치는 수행하지 않았다. GitHub CI의 새 runner에서는 setup부터 별도 후보 이미지 실행·승격까지 검증하며 고정 커밋 근거는 기술 설명 문서에서 확인한다. 반복 시연은 합성 정책·실행·감사 기록을 추가하므로 기존 기록을 보존하면서 필요한 횟수만 실행한다.

## 시연 영수증과 실행 결합 — v0.114

기본·기준 비교·역할 시연 모두 Ed25519 서명 검증 뒤 서명된 요청과 결과를 실제 요청 및 화면에 표시하는 응답과 대조한다. 후보 실행 ID·스냅샷 해시·결과 해시가 방금 완료한 실행과 일치해야 한다. 요청하지 않은 기준 근거, 다른 실행의 유효한 서명, 서명 범위 밖에서 바뀐 승인·판정은 시연 성공으로 처리하지 않는다. 공개키는 1 KiB 이하의 정규 UTF-8 Ed25519 SPKI 파일로 검증한 후 로그인한다. 이 검사는 합성 시연의 신뢰성을 보완하며 실제 배포 허가를 대신하지 않는다.

## 과거 검증 기록에서 평가 근거로 이동 — v0.115

CI 릴리스 검증 기록의 전체 기록 UUID를 확인하고 ‘후보 평가 근거 보기’를 누르면 현재 조직·프로젝트 권한으로 해당 실행을 다시 조회한다. 기준 비교가 있는 기록은 ‘기준 평가 근거 보기’도 제공한다. 목록을 여러 페이지 거슬러 찾거나 실행 UUID를 복사해 다시 입력하지 않아도 근거를 열 수 있다. 기록의 과거 통과 판정은 현재 최종 게이트에 복원하지 않는다. 이동한 실행의 릴리스 허용 여부는 새 최종 게이트 요청으로 확인한다.

잘못된 UUID·접근 불가·다른 실행의 응답은 기존 근거 선택을 유지한다. 중복 이동을 억제하며 조회 중 다른 실행 선택·프로젝트 전환·로그아웃이 일어나면 이전 응답을 표시하지 않는다. 이 기능은 평가 근거 조회이며 서명 검증이나 배포를 수행하지 않는다.

## 서명 근거 묶음 저장과 오프라인 검증 — v0.116

```powershell
npm.cmd run demo:evidence
# 기본 흐름만 묶음으로 저장하려면
npm.cmd run demo:portfolio -- --export-receipts
# 기록된 directory와 manifestSha256를 별도 검토에 사용
npm.cmd run demo:evidence:verify -- .local/portfolio-evidence-<UUID> .local/receipt-signing/public.pem <manifestSha256>
```

`demo:evidence`는 기준 비교 시연을 완료하고 자체 세션을 종료한 뒤 여섯 영수증과 목록을 새 `.local/portfolio-evidence-<UUID>` 폴더에 저장한다. 실제 별도 CLI 프로세스가 지정 공개키·출력된 목록 SHA-256으로 파일 여섯 개의 해시·Ed25519 서명·조직/프로젝트·실행 결합·통과/차단·승인 전후 순서를 검증한다. 기본 흐름은 `--export-receipts`, 비교 흐름은 `--compare --export-receipts`로 저장할 수 있다. 묶음은 API에서 받은 서명 요청·판정·증거 해시를 보존하며 평가의 원문 입출력이나 접근 키·서명 비밀키를 포함하지 않는다.

검증기는 네트워크를 사용하지 않고 독립적으로 신뢰한 공개키 경로를 요구한다. 목록은 별도로 서명되지 않는다. 선택적으로 제공하는 **예상 목록 SHA-256은 검토자가 다른 신뢰 경로로 확보해야** 묶음의 구성까지 고정한다. 묶음 안의 값을 그대로 신뢰하면 구성의 독립적 인증이 아니다. 예상 해시를 생략하면 각 영수증의 서명과 일관성만 확인하며 출력의 `expectedManifestDigestMatched`는 false다. 저장 명령과 검증 명령을 같은 시연 프로세스에서 연결한 확인은 독립 검토자의 신뢰 설정을 증명하지 않는다.

파일명이 정해진 여섯 JSON과 목록만 허용하며 경로 이동·추가 파일·누락·잘못된 UTF-8·크기 초과·다른 키·변조·서명 유효하더라도 모순인 판정이나 승인 근거를 거절한다. 완료·실행 정리·로그아웃 실패 시 묶음을 발행하지 않는다. 목록은 마지막에 독점 생성한다. 디스크 오류로 생긴 미완성 폴더는 성공으로 처리하지 않으며 기존 파일을 덮어쓰지 않는다. 이것은 과거 서명 근거 검증이다. 현재 승인 유효성, 실제 고객 모델 실행, 상용 배포 권한을 확인하지 않는다.

## 합성 프로젝트와 생성 실행의 고정 — v0.117

기본·비교·묶음 시연은 로컬 설정에 기록된 합성 프로젝트를 요청 헤더로 명시한다. 로그인 뒤 역할·조직·프로젝트를 확인한 뒤 카탈로그나 생성 API를 사용한다. 역할 시연도 네 세션 각각의 지정 조직·프로젝트·역할을 확인한다. 설정 오류나 세션 범위 불일치는 시연을 차단하고 발급받은 자체 세션을 종료한다.

평가 완료 응답은 처음 생성한 실행 ID 및 에이전트·데이터셋·정책 버전과 일치해야 한다. 응답이 달라도 정리 대상은 처음 생성한 실행으로 유지하며 다른 실행을 취소하지 않는다. 기본·비교·역할 시연의 요청 결합과 실패 정리를 테스트했다. 원래 응답 ID를 받지 못한 통신 중단의 생성 여부까지 발견하는 기능은 아니다.
